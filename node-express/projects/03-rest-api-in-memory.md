# Project 3: Bookmarks REST API (In-Memory)

## Description

Build a complete REST API for managing bookmarks — the kind of thing a "read it later" app would sit on top of. Each bookmark has a title, a URL, a list of tags, and a creation timestamp. The API supports the full CRUD lifecycle (create, read one, read many, update, delete), filters bookmarks by tag via a query string, validates every piece of input before touching your data, and reports failures through a single centralized error handler with one consistent error shape.

There is deliberately **no database** in this project. Bookmarks live in a plain in-memory array and vanish when the server restarts — that's fine. The point is to get the *HTTP layer* right: routing, status codes, validation, and error handling. Project 4 adds persistence to this exact API, so everything you build here gets reused.

When finished, you'll be able to drive the whole API from a REST client (or `Invoke-RestMethod` in PowerShell) and every request — valid, invalid, or aimed at something that doesn't exist — will get a correct, predictable response.

A bookmark in responses should look something like:

```json
{
  "id": 3,
  "title": "MDN HTTP status codes",
  "url": "https://developer.mozilla.org/en-US/docs/Web/HTTP/Status",
  "tags": ["reference", "http"],
  "createdAt": "2026-07-24T15:30:00.000Z"
}
```

## Requirements

Work top to bottom — each group builds on the previous one.

**Setup & skeleton**

- [ ] New npm project with `"type": "module"`, Express installed, and an npm `dev` script that runs the server with `node --watch`
- [ ] Server starts on a port read from `process.env.PORT` with a sensible fallback, and logs the URL it's listening on
- [ ] `express.json()` is applied so JSON bodies parse automatically
- [ ] `morgan` logs every request in the `dev` format
- [ ] A `GET /api/health` route returns `200` with a small JSON body, proving the skeleton works end to end

**Design before code**

- [ ] Before writing any route handlers, write the full endpoint table (method, path, purpose, success status, possible error statuses) as a comment or a `API.md` file — Chapter 7 style
- [ ] Bookmarks live in an in-memory array; IDs are generated by the server (incrementing number or a generated string — your choice, but the client never supplies one)

**Read endpoints**

- [ ] `GET /api/bookmarks` returns `200` and an array of all bookmarks (empty array — not `404` — when there are none)
- [ ] `GET /api/bookmarks?tag=<tag>` returns only bookmarks whose tags include that tag
- [ ] `GET /api/bookmarks/:id` returns `200` with the bookmark, or `404` with the standard error shape when no bookmark has that ID

**Create**

- [ ] `POST /api/bookmarks` validates the body: `title` is a non-empty string, `url` is a string that parses as a valid URL, `tags` is optional but must be an array of non-empty strings if present
- [ ] Validation uses zod **or** careful manual checks (pick one and be consistent) — either way, a bad body never reaches the "save" step
- [ ] Invalid bodies get `400` (or `422` — pick one and use it everywhere) with the standard error shape, including which field(s) failed and why
- [ ] Valid creates return `201`, a `Location` header pointing at the new resource, and the full created bookmark (with server-generated `id` and `createdAt`) in the body
- [ ] Unknown fields in the request body are stripped or rejected — the client cannot set `id` or `createdAt`

**Update & delete**

- [ ] `PUT /api/bookmarks/:id` (or `PATCH` — decide and document which, and why) validates like `POST`, returns `200` with the updated bookmark, or `404` if the ID doesn't exist
- [ ] `DELETE /api/bookmarks/:id` returns `204` with no body on success, `404` if the ID doesn't exist
- [ ] `DELETE` on an already-deleted ID returns `404` — confirm you understand why this is still considered idempotent

**Errors, centralized**

- [ ] One error-handling middleware (the 4-argument kind) is the *only* place that formats error responses
- [ ] Every error response in the whole API has the same JSON shape (e.g., an `error` object with `message` and optionally `details`) — verify by triggering a 400, a 404, and a deliberate thrown error and comparing
- [ ] Route handlers signal failures by throwing/`next(err)`-ing, not by hand-rolling `res.status(...).json(...)` in each handler
- [ ] A request to any undefined route (e.g., `GET /api/nope`) returns `404` in the standard shape, not Express's default HTML
- [ ] Malformed JSON in a request body (send `{"title": ` and stop) returns a `400` in your standard shape, not a crash or an HTML stack trace
- [ ] The error handler never leaks stack traces to the client

**Verification pass**

- [ ] Drive every endpoint (success + at least one failure each) from a REST client or `Invoke-RestMethod`, and check status codes — not just bodies — match your endpoint table

## Hints

- Write the endpoint table *first*, honestly. Most of the bugs you'd otherwise write are actually design ambiguities ("what does updating a missing bookmark return?") that the table forces you to settle up front. Chapter 7's design-on-paper section is the template.
- The consistent-error-shape requirement is easier if you create a tiny `HttpError` (or similar) class with a status code, throw it from handlers, and let the error middleware read `err.status`. Chapter 8 covers the pattern — resist copying, re-derive it.
- Async handlers that throw don't automatically reach your error middleware in Express 4 — reread Chapter 8's async section and decide how you'll handle it (wrapper function, or Express 5's built-in behavior; check which Express version you actually installed).
- For URL validation without a library: the global `URL` constructor throws on garbage. Think about what URL-ish strings you want to *reject* that it would accept (is `ftp://x` a bookmark?).
- `PUT` vs `PATCH`: Chapter 7. The honest answer is "either works for this project" — what matters is that your validation matches your choice (full replacement vs partial update).
- Testing from PowerShell: `Invoke-RestMethod` sends JSON with `-Method Post -ContentType "application/json" -Body ($obj | ConvertTo-Json)`. Note that PowerShell throws on non-2xx responses — `-SkipHttpErrorCheck` (PowerShell 7+) lets you inspect error responses instead.
- If your tag filter feels awkward, ask: should `?tag=` (empty) filter or not? Should an unknown tag return `[]` or `404`? (Chapter 7 has an opinion — collections filter, they don't 404.)

## Stretch Goals

- Add pagination to `GET /api/bookmarks` (`?limit=` and `?offset=`) with validated, bounded values and a response envelope that includes total count.
- Support filtering by multiple tags (`?tag=a&tag=b`) and decide — and document — whether that means "any of" or "all of".
- Add a `PATCH /api/bookmarks/:id/visits` style action or a `visitCount` field, and think through what method/path an "increment" operation deserves in REST terms.
- Write a `requests.http` file (VS Code REST Client extension) or a PowerShell script that exercises every endpoint, so the whole API can be smoke-tested in one go.
- Add an `X-Request-Id` middleware that attaches a unique ID to every request and includes it in error responses and morgan logs.
